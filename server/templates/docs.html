MinersWorldCoin API documentation

Reference for the REST endpoints, Esplora-compatible routes, and Socket.IO events exposed by this Python server.

REST base URL: https://api.minersworld.org. The root page is the interactive API explorer; its request cards remain unchanged.

Machine-readable contract: OpenAPI 3.1 YAML. Existing paths remain available; the main REST routes also have versioned aliases under /api/v1, where JSON responses use a standard envelope and JSON errors use HTTP error statuses. The /api/v1/esplora aliases preserve Esplora response formats.

Response and amount conventions

Most REST methods return an object containing result, error, and id (normally api-server). Node errors are returned in error. A few endpoints intentionally return plain text, arrays, or a different JSON shape; these are called out below.

In the main API, monetary amounts are integer satoshis: 1 MWC = 100,000,000 satoshis. Keep amounts as integers when building transactions. The /price endpoint is a CoinPaprika response in market units, not satoshis. The /supply/plain endpoint returns whole MWC as plain text.

The explorer adds a circulating-supply equivalent in MWC alongside the raw satoshi supply. The API's JSON response remains unchanged.

Constructing, signing, and broadcasting transactions

This server does not create transactions or sign them. It provides UTXO lookup, transaction decoding, and a node relay for already-signed raw transaction hex. Private keys stay in the wallet or signing client.

  1. Call GET /unspent/{address} to retrieve spendable outputs. Each output identifies its source with txid and index (the vout) and includes the locking script and value in satoshis. Use an amount filter only if useful; amount is integer satoshis.
  2. Select inputs whose total covers the recipient amount and fee. Construct outputs for the recipient and, if needed, a change address you control. The difference between input total and output total is the transaction fee. Recheck inputs immediately before signing because another spend can invalidate them.
  3. Build and sign with a wallet library configured for MWC's address and transaction rules. Each input must spend the referenced output and be signed by the key that controls it. Use the wallet's supported scripts and signature-hash behavior; this API cannot sign for you.
  4. Call GET /decode/{raw-hex} on the signed transaction and inspect inputs, outputs, amounts, and change before broadcasting. Decoding only parses the transaction; it does not promise mempool acceptance.
  5. POST the signed hex to /broadcast as URL-encoded form field raw, or as JSON {"raw":"…"}. The Python handler passes it to the node's sendrawtransaction RPC. On success, the node returns a transaction ID. A returned ID means accepted by that node, not confirmed in a block.
  6. Track the transaction with /transaction/{txid} and the address with /mempool/{address}. After it is mined, transaction details include block metadata and confirmations.

The legacy /fee route remains hard-coded to feerate: 1000000 and blocks: 30. That value is 1,000,000 satoshis (0.01 MWC), not a per-byte quote from current mempool conditions. Use /fee-estimates for the node's current smart-fee estimates in sat/vB; estimate availability depends on node history.

The companion MWC API and wallet project documents these network parameters for wallet configuration: public-key address prefix 20, script address prefix 10, WIF prefix 123, extended public/private key versions 0488B21E/0488ADE4, and Bech32 HRP mwc. Bitcoin mainnet defaults will derive incompatible addresses. 

curl "https://api.minersworld.org/unspent/98AUvgXPjAdKHj3FqwAPJNpd8XergXBL59"

curl -X POST "https://api.minersworld.org/broadcast" \
  --data-urlencode "raw=SIGNED_RAW_TRANSACTION_HEX"

For an Esplora-style relay, POST /esplora/tx instead expects the raw hex directly as a plain-text request body and returns the txid as plain text.

Socket.IO events

Connect a Socket.IO client to the API origin using the default /socket.io path. Request handlers return their result through the event acknowledgement. Arguments are positional: send a string, number, or array as appropriate rather than an object with named fields. Connection and disconnection lifecycle events are handled automatically by the server.

EventArgument(s)Behavior
